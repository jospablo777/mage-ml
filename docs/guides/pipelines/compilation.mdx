Compilation is a performance optimization. MageML checks a pipeline's blocks for errors and
builds them ahead of its production runs (triggers, schedules, backfills and API runs), so
those runs start without building anything and run faster. Running a block in the editor is
unchanged.

## What compiling does

| Blocks | What happens |
| --- | --- |
| Python | Each block is checked for syntax errors; a block without its decorated function gets a warning |
| R | Each block is parsed with R; the project's R environment is checked and prepared |
| Rust | Consecutive Rust blocks build into one program whose queries Polars plans together; a Rust block that something else needs on its own (it has tests, it is an exporter, it uses another database profile) builds as its own program |
| SQL | Consecutive DuckDB or PostgreSQL SQL blocks that replace their tables chain: each but the last becomes a view, and the last writes its table from one query the database plans across them ([below](#sql-chains)). Other databases run each block as written |

In production runs, blocks of the same language that follow each other run as one chain:
consecutive Rust blocks as one program, consecutive R blocks in one R session, and Python
blocks in one process. Each switch between languages ends a chain and converts the data, so
a pipeline in one language runs fastest. See
[Pipeline performance](/production/pipeline-performance) for the measurements.

## SQL chains

In a production run, a DuckDB or PostgreSQL SQL block followed in its stage by a SQL block
of the same database and connection profile becomes a view of its query instead of a
table, when nothing needs its own rows. The block that needs them, such as an exporter,
writes its table from one query: the database inlines the views and plans the chain as one
statement, so filters and column choices reach the first block's source and no
intermediate table is written.

A chain of four blocks, on a laptop (Apple M4 Pro):

| Database | Run | Time | Stored |
| --- | --- | --- | --- |
| DuckDB, 30 million rows | Each block writes its table (`MAGE_COMPILED_CHAINS=off`) | 20 s | 952 MB |
| | Compiled: three views and the exporter's table | 1.0 s | 1 MB |
| PostgreSQL 16, 5 million rows | Each block writes its table | 16 to 19 s | 613 MB |
| | Compiled | 2.6 to 3.5 s | 16 kB |

- Only blocks that replace their tables chain (write policy **replace**). A block that
  appends keeps its table, because the rows it accumulates over runs are what the blocks
  after it read; the Compile panel lists it with the reason.
- A block whose own rows are needed writes its table: an exporter, a block with a data
  contract or monitors, or every block when the pipeline keeps every output.
- Raw SQL blocks, dynamic blocks and other databases run each block as written. The
  Compile panel says so: for now, compiling SQL block chains supports DuckDB and
  PostgreSQL.
- The views keep the blocks' table names, so other readers of the database still find
  them. Running a block in the editor writes its table again in place of its view.
- PostgreSQL does not drop a table or view that a view reads. MageML marks its chain
  views with a comment (`MageML compiled chain view`), and a block that replaces its
  table first drops the chain views that read it; the blocks after it create them again
  in the same run. A view of your own over a chain block is never dropped: the run fails
  instead, and PostgreSQL's error names the view. Build such views on the exporter's
  table, which stays a table.
- `MAGE_COMPILED_CHAINS=off` turns chains off for Rust, R and SQL.

## Single-language and polyglot pipelines

<Frame>
  <img className="block dark:hidden" src="/images/diagrams/single-vs-polyglot.light.svg" alt="The same five-step pipeline in Python only, one chain with no conversions, and in Python, Rust and R, four chains with three Arrow conversions" />
  <img className="hidden dark:block" src="/images/diagrams/single-vs-polyglot.dark.svg" alt="The same five-step pipeline in Python only, one chain with no conversions, and in Python, Rust and R, four chains with three Arrow conversions" />
</Frame>

A pipeline in one language compiles into one chain: one process, and each block hands its
frame to the next in memory. A pipeline in several languages has one chain per run of
blocks in the same language. Each switch starts another process (a Rust program or an R
session) and converts the data through Apache Arrow.

Measured on a laptop (Apple M4 Pro):

| Pipeline | Rows | Run | Time |
| --- | --- | --- | --- |
| The [tutorial](/getting-started/polyglot-pipeline) pipeline, Python only | 200,000 | `mage run` | 1.8 s |
| The same pipeline in Python, Rust and R | 200,000 | `mage run` | 3.2 s |
| Five pandas blocks | 3,000,000 | exported service | 0.68 s |
| The same with the first two blocks in Rust | 3,000,000 | exported service | 0.78 s |
| The same with the first four blocks in Rust | 3,000,000 | exported service | 0.51 s |
| Five Rust blocks | 3,000,000 | exported service | 0.24 s |

On small tables the switches cost more than the work. On large tables, a faster language
on the heavy steps pays for its switches, but only once it holds every step that touches
the full table: two Rust blocks between pandas blocks were slower than none.

| | Single-language | Polyglot |
| --- | --- | --- |
| Speed | No switches: the fastest a language allows | Each switch costs a process start and a conversion; worth it when a faster language takes the heavy steps |
| Memory | One frame passed along a chain | A converted copy at each switch |
| Libraries | One ecosystem | The best library for each step: Rust and Polars for large tables, R for statistics, Python for ML and connectors |
| People | One language to read, review and debug | Readers need each language in the pipeline |

Rules of thumb:

- Write a pipeline in one language unless a step needs another.
- Switch languages where the data is small, such as after an aggregate.
- Move a whole run of heavy steps to Rust, not one block in the middle.
- The Compile panel shows a pipeline's languages in order, such as `Python → Rust ×2 → R`,
  and suggests a single language when it would run faster.

[Pipeline performance](/production/pipeline-performance) has the full measurements,
including memory.

## When it runs

You rarely need to start it:

- **After you save** a block or the pipeline, once saves stop for 3 seconds.
- **When you turn on a trigger**, so its first scheduled run does not wait for a build.
- **When the server starts**, for pipelines with an active trigger. Set
  `MAGE_COMPILE_ON_START=off` to skip it.
- **When you ask**: **Compile now** in the panel, or **Compile** in a pipeline's right-click
  menu in the pipelines list.

A compilation for code that has not changed reuses what was built, so it finishes in
seconds.

## See the result

The button next to the kernel in the editor header shows the state:

| Button | Meaning |
| --- | --- |
| **Compile** | Not compiled yet, or the code changed since the last compilation |
| **Compiling** | A compilation is running; the panel shows its progress |
| **Compiled** | Compiled, and the code has not changed since |
| **Compile failed** | A block has an error; the panel shows it with the file and line |
| **Optimized** | Nothing to compile: the pipeline has no Python, R or Rust blocks |

Click it to open the panel. It lists each step with its result (passed, built, up to date or
failed) and time, when the pipeline last compiled and whether the code changed since, and
the pipeline's languages in order, such as `Python → Rust ×2 → R ×2`, with a hint when a
single-language pipeline would run faster.

## When it fails

Fix the error the panel shows and save; the pipeline compiles again on its own. A failed
compilation does not stop a production run from starting: Rust blocks build when they first
run instead, and the run reports any error in the block's log.

## From the API

```text
POST /api/pipeline_compilations   {"pipeline_compilation": {"pipeline_uuid": "sales"}}
GET  /api/pipeline_compilations/sales
```

The POST starts a compilation; the GET returns its progress and result.
