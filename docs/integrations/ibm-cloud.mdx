MageML works with IBM Cloud without IBM's SDKs. IBM services that speak open protocols (S3,
Kafka, PostgreSQL) are reached through the same clients as anywhere else, with IBM's
differences handled for you: IAM tokens, COS's limits on the S3 API, and the private CAs of
IBM Cloud Databases.

| Service | In MageML | In exported services |
| --- | --- | --- |
| [Cloud Object Storage](#cloud-object-storage) | Data loader and exporter blocks; block outputs and logs; `IBMCloudObjectStorage` in code | Blocks run as in MageML |
| [MLflow on COS](#mlflow-artifacts-in-cos) | Built in (`cos://` artifact locations) | Built in |
| [Event Streams](#event-streams) | Streaming pipelines (Kafka source and sink) | Kafka source and sink in Rust |
| [IBM MQ](#ibm-mq) (on Cloud or your own) | Streaming pipelines (`mage-ml[ibm-mq]`) | IBM MQ source and sink in Rust |
| [Db2](#db2) (Db2 on Cloud, Db2 Warehouse) | SQL blocks, loaders and exporters (`mage-ml[db2]`) | Blocks run as in MageML |
| [Cloud Databases for PostgreSQL](#cloud-databases) | SQL blocks, loaders and exporters, with TLS verified | Blocks run as in MageML |
| [Secrets Manager](#secrets-manager) | | `ibm:` secret references |
| [Code Engine, Container Registry, IKS, OpenShift](#run-services-on-ibm-cloud) | | Deploy scripts, Tekton pipeline, manifests |

Only Db2 and IBM MQ need drivers of their own; `uv pip install "mage-ml[ibm]"` installs
both (`mage-ml[db2]` and `mage-ml[ibm-mq]` one at a time). Everything else works with the
core install.


## Credentials

Every IBM Cloud API takes an IAM access token. MageML gets one from either of:

| Credential | Use it for | Notes |
| --- | --- | --- |
| A **service ID API key** | MageML servers, CI, anything outside IBM Cloud | Give the service ID only the roles it needs. Prefer it to a personal API key, which carries all of that user's access and leaves with them. |
| A **trusted profile** | Code Engine apps and jobs, IKS and OpenShift pods | No key is stored: the platform mounts a compute resource token that IAM exchanges. Set `IBM_CLOUD_TRUSTED_PROFILE` to the profile id (`Profile-...`) or name. |
| **HMAC keys** (COS only) | Tools that need AWS signatures: DuckDB, Polars, pyarrow, presigned URLs | Created with the COS service credential ("Include HMAC credential"). They never expire, so rotate them yourself. |

Tokens last an hour. MageML caches each one and replaces it five minutes before it expires,
also on retries, so long runs and streams never send an expired token.

Inside IBM Cloud, set `IBM_CLOUD_IAM_URL=https://private.iam.cloud.ibm.com` to keep token
requests on the private network.

## Cloud Object Storage

### Set up

1. Create a bucket and note its **endpoint**: in the bucket's Configuration tab, or in the
   endpoints list. Endpoints are per region and per network:

   | Endpoint | Reaches COS from | Example |
   | --- | --- | --- |
   | Public | Anywhere | `https://s3.us-south.cloud-object-storage.appdomain.cloud` |
   | Private | IBM Cloud classic and VPC networks | `https://s3.private.us-south.cloud-object-storage.appdomain.cloud` |
   | Direct | VPC, without public egress | `https://s3.direct.us-south.cloud-object-storage.appdomain.cloud` |

   From inside IBM Cloud, use the private or direct endpoint: traffic to them is not billed as
   public bandwidth and never leaves IBM's network.
2. Create a service credential with the **Writer** role (or **Reader** for loaders only), with
   HMAC on if you want HMAC keys. Better: give a service ID or trusted profile the role on the
   one bucket, not the whole instance.
3. Add the settings to `io_config.yaml`:

```yaml
default:
  IBM_COS_ENDPOINT: https://s3.us-south.cloud-object-storage.appdomain.cloud
  # Either HMAC keys:
  IBM_COS_HMAC_ACCESS_KEY_ID: "{{ env_var('IBM_COS_HMAC_ACCESS_KEY_ID') }}"
  IBM_COS_HMAC_SECRET_ACCESS_KEY: "{{ env_var('IBM_COS_HMAC_SECRET_ACCESS_KEY') }}"
  # Or an API key (or IBM_CLOUD_TRUSTED_PROFILE on Code Engine and IKS):
  IBM_CLOUD_API_KEY: "{{ env_var('IBM_CLOUD_API_KEY') }}"
  # The instance CRN: needed only to list or create buckets with an API key.
  IBM_COS_INSTANCE_ID: crn:v1:bluemix:public:cloud-object-storage:global:a/...
```

HMAC keys win when both are set.

### Load and export

Add a block from **Data loader > Data lakes > IBM Cloud Object Storage** (or the exporter of
the same name), or in code:

```python
from mage_ai.io.config import ConfigFileLoader
from mage_ai.io.ibm_cos import IBMCloudObjectStorage

storage = IBMCloudObjectStorage.with_config(ConfigFileLoader(config_path, 'default'))
orders = storage.load('lake', 'orders/2026/10/orders.parquet')
storage.export(orders, 'lake', 'orders/clean/orders.parquet')
```

CSV, JSON, Parquet and HDF5 are read and written as with the S3 blocks, with the same
options (`exact_types=True`, `polars=True`).

For a boto3 client of your own: `mage_ai.services.ibm.cos.client(endpoint_url, api_key=...)`.

### MageML's own files in COS

Block outputs (`remote_variables_dir`) and logs can live in COS. MageML uses a COS client
whenever the S3 endpoint is a COS endpoint, so `s3://` paths work with either kind of
credentials:

```yaml
# metadata.yaml
remote_variables_dir: s3://mage-outputs/shop
logging_config:
  type: s3
  destination_config:
    bucket: mage-logs
    prefix: shop
    endpoint_url: https://s3.private.us-south.cloud-object-storage.appdomain.cloud
```

```bash
# The endpoint for remote_variables_dir, and the credentials for both.
export AWS_ENDPOINT_URL_S3=https://s3.private.us-south.cloud-object-storage.appdomain.cloud
export IBM_CLOUD_API_KEY=...        # or IBM_CLOUD_TRUSTED_PROFILE, or HMAC keys as
                                    # AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY
```

### HMAC keys or IAM

| | HMAC keys | API key or trusted profile |
| --- | --- | --- |
| Works with | Every S3 tool: boto3, DuckDB, Polars, pyarrow, Spark, rclone | boto3 through MageML; MageML's blocks and MLflow plugin |
| Presigned URLs | Yes | No |
| Revocation | Delete the credential | Disable the key or profile; tokens already issued last up to an hour |
| Rotation | By hand | Keys by hand; trusted profiles need none |
| Access control | The credential's role on the instance | IAM policies on the bucket, groups, conditions |
| Common policy | Some organizations forbid long-lived HMAC keys | Allowed |

Use IAM (trusted profiles on Code Engine and IKS, service ID keys elsewhere) unless a tool needs
AWS signatures. Then create HMAC keys for that tool only, on a service ID scoped to its buckets.

### Gotchas

- **COS is not boto3-compatible as it comes.** IAM credentials need a bearer token instead of
  an AWS signature; IBM ships a fork of boto3 for it. MageML adds the token with botocore hooks
  scoped to your COS endpoint, so plain boto3 works, and clients for other hosts in the same
  process (AWS S3 included) are untouched. Do not swap `boto3` for `ibm_boto3` in
  `sys.modules`: it breaks every AWS client in the process.
- **boto3 1.36 and later add CRC checksums to uploads**, which COS fails (`MissingContentLength`,
  `InvalidRequest`). MageML's COS clients send checksums only where an operation requires them.
  In your own clients, set `request_checksum_calculation` and `response_checksum_validation` to
  `when_required` in the botocore `Config`, or `AWS_REQUEST_CHECKSUM_CALCULATION` and
  `AWS_RESPONSE_CHECKSUM_VALIDATION`.
- **Bucket locations name a storage class**: `LocationConstraint` is `us-south-standard`,
  `eu-de-smart` and so on, not an AWS region. Create buckets in the console or with Terraform;
  the region in clients is not used.
- **Listing and creating buckets with an API key** need the instance CRN
  (`IBM_COS_INSTANCE_ID`); object operations do not.
- **Cold and Vault classes charge for retrieval** and have minimum storage durations. Use
  Smart Tier for data whose access pattern you do not know.
- **Archive** (Glacier-like) objects must be restored before reads; a load fails until then.
- Key Protect or Hyper Protect Crypto Services encryption is set on the bucket at creation and
  needs nothing in MageML.

## MLflow artifacts in COS

MageML registers a `cos` artifact scheme with MLflow, so runs log to and read from
`cos://<bucket>/<path>` with any of the credentials above:

```bash
export IBM_COS_ENDPOINT=https://s3.private.us-south.cloud-object-storage.appdomain.cloud
export IBM_CLOUD_TRUSTED_PROFILE=Profile-...    # or IBM_CLOUD_API_KEY, or the HMAC keys
```

**An MLflow server of its own**, without MageML, installs only the plugin, a few small modules
on boto3 and requests:

```bash
uv pip install "mlflow-ibm-cos @ git+https://github.com/jospablo777/mage-ml#subdirectory=packages/mlflow-ibm-cos"
mlflow server --artifacts-destination cos://models/mlflow --backend-store-uri postgresql://...
```

MLflow and MageML stay independent: either one can be upgraded or moved without the other.
The plugin is MageML's own code, built into its own package, and works with MLflow 2.9 and
later.

- **Existing `s3://` locations on COS keep working.** When `MLFLOW_S3_ENDPOINT_URL` is your COS
  endpoint, the plugin makes MLflow's S3 client use IAM tokens. This replaces
  `sitecustomize.py` patches that swap boto3 for IBM's fork.
- With IAM credentials, MLflow cannot hand out presigned URLs, so keep the artifact proxy on
  (the default with `--artifacts-destination`), or give the server HMAC keys.
- Clients that only talk to a proxying server (`mlflow-artifacts:` locations) need no COS
  settings at all.

## Event Streams

Event Streams is Kafka. A streaming pipeline's Kafka source and sink take the service
credentials JSON (the service key IBM Cloud makes) as one setting, which stands for the
brokers and the sign-in:

```yaml
connector_type: kafka
event_streams_credentials: "{{ env_var('EVENT_STREAMS_CREDENTIALS') }}"
topic: orders
consumer_group: orders-clean
```

Set `EVENT_STREAMS_CREDENTIALS` to the JSON, for example
`ibmcloud resource service-key orders-key --output JSON | jq -c '.[0].credentials'`. The
brokers come from `kafka_brokers_sasl`, and the sign-in is SASL PLAIN as `token` with the
`api_key`. The same settings written out:

```yaml
connector_type: kafka
bootstrap_server: "{{ env_var('EVENT_STREAMS_BROKERS') }}"   # kafka_brokers_sasl, comma separated
topic: orders
consumer_group: orders-clean
security_protocol: SASL_SSL
sasl_config:
  mechanism: PLAIN
  username: token
  password: "{{ env_var('EVENT_STREAMS_API_KEY') }}"
```

- Credentials written in the file are refused by `mage export service`.
- Exported services run the same settings in their Rust Kafka connector; the key stays an
  `env_var()` reference that the service reads, never written into the image.
- Create topics in the console, CLI or Terraform, with the partitions you need: each plan
  limits topics and partitions.
- Throughput is limited per partition by plan. Scale a stream by partitions and service
  instances, up to one instance per partition.
- Retention is set per topic. A consumer group that falls behind past it loses data; watch the
  lag in the service console.
- Use the private endpoints from inside IBM Cloud (the credentials of a private service
  endpoint list them).

## IBM MQ

Streaming pipelines read from and write to IBM MQ queues, on IBM MQ on Cloud or any queue
manager you run:

```yaml
connector_type: ibm_mq
queue_manager: QM1
channel: APP.SVRCONN
connection_name: "qm1.example.com(1414)"   # host(port), comma separated for multi-instance
queue: ORDERS.IN
user: orders
password: "{{ env_var('MQ_PASSWORD') }}"
cipher_spec: ANY_TLS12_OR_HIGHER          # TLS; leave out with key_repository for plain text
key_repository: /etc/mq/keys/client       # the key database, without .kdb
batch_size: 200                           # source: messages per batch
batch_timeout: 0.5                        # source: seconds before a smaller batch runs
connections: 1                            # source: connections reading in parallel
```

The same file runs in MageML and in exported services. On IBM MQ on Cloud, the user is the
application's MQ user name and the password its API key; the channel and connection come from
the queue manager's connection information, and its TLS certificate goes into the key
database (`runmqakm -cert -add`).

### How messages are acknowledged

- The source reads under syncpoint and commits only after every sink took the batch. A
  stream that stops, fails or dies leaves the batch on the queue: the queue manager backs out
  a dead connection's unit of work. A normal disconnect would commit it, so the source backs
  out before every disconnect.
- A unit of work belongs to its connection, so each connection has one batch in flight and
  reads the next after the commit. `connections` reads in parallel; with more than one, queue
  order holds only within a batch. Keep one where order matters.
- `batch_size` must not exceed the queue manager's `MAXUMSGS` (10000 by default), the most
  messages one unit of work holds.
- The sink puts persistent messages under syncpoint and commits the batch as its receipt.
  Each MsgId is derived from the stream and the input's position, the same when a batch is
  written again after a restart, so consumers can drop duplicates by MsgId.
- Text messages are converted to UTF-8 by the queue manager. Binary messages that are not
  UTF-8 stop the stream rather than being changed.
- Blocks get each message's value (JSON, or the text). Message properties are not passed yet.

### Where it runs

| | Needs |
| --- | --- |
| Exported services | Nothing: the image downloads IBM's redistributable MQ client (pinned version, checked against its SHA-256) and the engine loads it. IBM publishes that client for Linux x86-64 only, so build those images with `docker build --platform linux/amd64`. |
| MageML | `uv pip install "mage-ml[ibm-mq]"` and the IBM MQ client: on macOS the MQ toolkit, on Linux the redistributable client, with its `lib64` on the library path (`LD_LIBRARY_PATH`, `DYLD_LIBRARY_PATH` on macOS). |

The engine builds without IBM's SDK and loads the client at run time, from
`MAGE_SERVICE_MQ_LIBRARY`, `MQ_HOME/lib64` or the library path.

### Gotchas

| Reason | What to check |
| --- | --- |
| 2035 `NOT_AUTHORIZED` | User and password, the channel's `CHLAUTH` rules, and the user's authority on the queue |
| 2085 `UNKNOWN_OBJECT_NAME` | The queue's name, which is case sensitive |
| 2059 `Q_MGR_NOT_AVAILABLE`, 2538 | The address and port; a firewall or allowlist in between. Retried with backoff. |
| 2024 `SYNCPOINT_LIMIT_REACHED` | `batch_size` above `MAXUMSGS` |
| 2053 `Q_FULL` | The output queue's `MAXDEPTH`; retried |
| 2393 `SSL_INITIALIZATION_ERROR` | `key_repository`, `certificate_label`, and a `cipher_spec` the channel's `SSLCIPH` accepts |

Messages that fail in a block and go back to the queue count up `BackoutCount`. Set the
queue's `BOTHRESH` and `BOQNAME` so the queue manager moves messages that keep failing to a
backout queue, or give the stream a dead-letter sink.

## Db2

Install the driver with `uv pip install "mage-ml[db2]"`. IBM's `ibm_db` wheels include its CLI
driver for macOS, Linux x86-64 and Windows; IBM builds none for Linux arm64, so run MageML
images that use Db2 as `linux/amd64`.

```yaml
default:
  DB2_HOST: 1a2b3c.databases.appdomain.cloud   # Db2 on Cloud: connection.db2.hosts[0]
  DB2_PORT: 30376                              # its TLS port
  DB2_DATABASE: bludb
  DB2_USER: "{{ env_var('DB2_USER') }}"
  DB2_PASSWORD: "{{ env_var('DB2_PASSWORD') }}"
  DB2_SCHEMA: ANALYTICS                        # optional; the user's schema by default
  DB2_SSL: true
  DB2_SSL_CERTIFICATE: "{{ env_var('DB2_CA_BASE64') }}"   # optional: base64, PEM or a path
```

Pick **IBM Db2** as a SQL block's data provider, or the **IBM Db2** loader and exporter
templates (`mage_ai.io.db2.Db2` in code).

- **Names.** Db2 folds unquoted names to upper case. Tables and columns are created unquoted,
  so your SQL needs no quotes, and loaded columns come back in lower case, so a frame keeps its
  column names through a round trip. SQL keywords (`select`, `order`, `user`), and names
  that do not start with a letter or hold other characters, are quoted, and keep their case.
- **Types** keep values exact: integers as `BIGINT`, or `DECFLOAT(34)` past 64 bits; decimals
  as `DECFLOAT(34)`; floats as `DOUBLE`; text as `VARCHAR` sized from the data, or `CLOB` past
  32,672 bytes; timestamps as `TIMESTAMP(6)`, time zones converted to UTC; lists and dicts as
  JSON text.
- **Upserts** (`unique_constraints` with `unique_conflict_method` `UPDATE` or `IGNORE`) are
  `MERGE` statements. Db2 requires the columns of a unique constraint to be `NOT NULL`, so they
  are created that way.
- **SQL blocks** write their upstream outputs as tables in `DB2_SCHEMA`, which the connection
  sets as the current schema, so blocks name them without a schema. An upstream Db2 SQL
  block's own table is named with the schema it sets, and a block's schema is where its own
  table goes. They run the same way in
  exported services, whose image then builds for `linux/amd64` only: `mage export` sets the
  platform in the manifest, the README's commands and the GitHub workflow, and the
  Dockerfile stops an arm64 build with the reason.
- **TLS.** Db2 on Cloud's certificate is from a public CA, so `DB2_SSL: true` is enough. For a
  server with a private CA, set `DB2_SSL_CERTIFICATE`. User and password are passed to the
  driver on their own, so they may contain `;`.
- Text keeps every character, emoji included: MageML sends it as UTF-8, as some `ibm_db`
  releases cut characters outside the Basic Multilingual Plane from text, or crash writing
  text to a `CLOB`. A database whose code set is not UTF-8 gets text as the driver sends it.
- Queries in blocks are limited with `FETCH FIRST n ROWS ONLY` around them.

Gotchas:

- `SQL30082N` (security processing failed): the user or password, or a user without
  `CONNECT` on the database.
- `SQL0551N`: no privilege on the table or schema; tables go to `DB2_SCHEMA`, which the user
  must be allowed to create in (`CREATEIN`).
- `SQL0911N` reason 2 (deadlock) or 68 (lock timeout): long-running writes to the same table
  from parallel blocks. Make them run in order, or write to separate tables.
- Db2 on Cloud plans limit connections; blocks that run in parallel each open one.

## Cloud Databases

IBM Cloud Databases for PostgreSQL serves TLS with IBM's own CA. Give MageML the certificate
from the service credentials (`certificate.certificate_base64`) as it is:

```yaml
default:
  POSTGRES_HOST: 1a2b3c.databases.appdomain.cloud     # connection.postgres.hosts[0].hostname
  POSTGRES_PORT: 31234                                # connection.postgres.hosts[0].port
  POSTGRES_DBNAME: ibmclouddb                         # connection.postgres.database
  POSTGRES_USER: "{{ env_var('PG_USER') }}"
  POSTGRES_PASSWORD: "{{ env_var('PG_PASSWORD') }}"
  POSTGRES_SSLMODE: verify-full
  POSTGRES_SSLROOTCERT: "{{ env_var('PG_CA_BASE64') }}"  # base64, PEM text, or a file path
```

- Use `verify-full`: it checks the certificate's name too, so a DNS mistake cannot send your
  password to another server. `require` encrypts but trusts any server.
- The certificate is written once to a private file, named by its hash; a rotated certificate
  gets a new file.
- Create a user per application instead of using the admin user from the credentials, and give
  it only the schemas it needs.
- Connections are limited by plan and memory. Pipelines with many parallel blocks can exhaust
  them; use PgBouncer or lower block concurrency.
- Private endpoints keep traffic off the public network; with an IP allowlist, add the
  addresses MageML connects from.

For MongoDB, Redis and MySQL, decode the certificate to a file and point the driver's TLS CA
option at it (for MongoDB, `tlsCAFile` in the connection string).

## Secrets Manager

In `io_config.yaml`, `ibm_secret_var` reads a secret, as `aws_secret_var`,
`azure_secret_var` and `gcp_secret_var` do for the other clouds:

```yaml
default:
  POSTGRES_USER: "{{ ibm_secret_var('3f1c9a2e-...', 'username') }}"
  POSTGRES_PASSWORD: "{{ ibm_secret_var('3f1c9a2e-...') }}"
```

MageML reads the instance from `IBM_SECRETS_MANAGER_URL` and authenticates with
`IBM_CLOUD_API_KEY` or `IBM_CLOUD_TRUSTED_PROFILE`; values are cached for five minutes, as
`io_config.yaml` is read for every block. Without a field, an arbitrary secret gives its
payload, a username and password secret its password, an IAM credentials secret its API key;
key-value secrets need the key. An exported service fetches the same secrets itself at
start-up: the export lists them in the manifest, so nothing more is configured than the
instance and the credentials below.

Exported services read other secrets from IBM Cloud Secrets Manager at start-up too:

```bash
MAGE_SERVICE_IBM_SECRETS_MANAGER_URL=https://<instance id>.us-south.secrets-manager.appdomain.cloud
MAGE_SERVICE_SECRETS='PGPASSWORD=ibm:<secret id>, PGUSER=ibm:<secret id>#username'
```

They authenticate with `IBM_CLOUD_API_KEY` or a trusted profile
(`MAGE_SERVICE_IBM_TRUSTED_PROFILE`). Give the identity the **SecretsReader** role on the
secret group only. See [secrets](/production/pipeline-services#configuration-and-secrets).

## Run services on IBM Cloud

`mage export service` writes deployment files for IBM Cloud next to each service:

- `deploy/ibm/code-engine.sh` builds the image and deploys it to Code Engine;
- `.tekton/` is a Continuous Delivery pipeline: build with kaniko, push to Container Registry,
  deploy to Code Engine by digest;
- `deploy/kubernetes.yaml` runs on IKS and OpenShift.

Push images to IBM Cloud Container Registry with `ibmcloud cr login`, or
`docker login -u iamapikey icr.io` with an API key. See
[exported services](/production/pipeline-services).

### Logs and metrics

A service writes its logs to its output and serves Prometheus metrics at `/metrics`, with no
token, so IBM Cloud's own collectors take them as they take any container's:

- **IBM Cloud Logs.** Set `MAGE_SERVICE_LOG_FORMAT=json` so each line is a JSON object with
  its run, block and level. On Code Engine, the logs reach IBM Cloud Logs once the region's
  platform logs are routed to a Cloud Logs instance. On IKS and OpenShift, the logging
  agent collects the containers' output.
- **IBM Cloud Monitoring.** On IKS and OpenShift, the monitoring agent scrapes pods with the
  `prometheus.io/scrape` annotations, which `deploy/kubernetes.yaml` sets, and keeps
  metrics such as `mage_service_stream_lag_messages` per stream and partition: alert on lag,
  or scale on it. Code Engine sends its platform metrics (CPU, memory, requests) to
  Monitoring; the service's own metrics need a scraper that reaches it.
- Runs, their logs and errors stay readable through the service's API and `mage-console`,
  whichever collector is set up.

## Good practices

- One service ID or trusted profile per workload, with the least roles, scoped to resource
  groups or buckets. Trusted profiles on Code Engine and IKS, so no keys are stored.
- Keep keys in Secrets Manager or Code Engine secrets, referenced with `env_var()`, never in
  `io_config.yaml`.
- Private endpoints for COS, Event Streams, databases and IAM when MageML runs in IBM Cloud.
- Put MageML, its databases and buckets in the same region: cross-region traffic is slower and
  billed.
- Rotate HMAC keys and API keys on a schedule; prefer credentials that expire.
