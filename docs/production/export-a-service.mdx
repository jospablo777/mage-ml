This guide takes two pipelines from a MageML project and turns them into one Docker service
that runs without MageML. It uses a small project, `shop`, with two pipelines:

- `load_orders`: generates orders and drops the ones with no amount;
- `daily_summary`: sums the orders by region, every hour (a time trigger).

Every command and output below comes from a real run. For every option, see the
[pipeline services reference](/production/pipeline-services).

## Before you start

- The pipelines run in MageML: `mage run shop load_orders` completes.
- Docker is installed. The machine that builds the image needs nothing else: Rust, R and
  Python packages are installed inside the image.

## Export from the app

The steps below use the CLI. The app does the same:

- **Export as service** in the pipelines list (right-click a pipeline) and in the editor's
  **File** menu opens a dialog: choose one or more pipelines and the dialog shows what the
  service will hold (blocks, schedules, packages, the environment variables to set) and
  anything that stops the export, before you export. The export shows its progress, then a
  download of the build context and the commands to build, run and call it.
- **Services**, in the left menu, saves services in the project's
  `pipeline_services.yaml`, with the pipelines, the [after-run triggers](/production/pipeline-services#after-run-triggers)
  that start one pipeline when another's run ends, and their settings. It checks the
  configuration as you change it, lists the secrets and variables the container needs, and
  shows how to keep run history, logs and metrics. The CLI exports a saved service with
  `mage export service . --service shop-live --out ./shop-live`.

## 1. Export

One pipeline:

```bash
mage export service shop load_orders --out ./orders-service
```

A group of pipelines in one service: list them and give the service a name.

```bash
mage export service shop load_orders daily_summary --out ./shop-service --name shop
```

The export prints what it found:

```text
Service shop, from project shop

load_orders: 2 blocks, at most 1 run(s) at once
  python data_loader   generate_orders
  python transformer   clean_orders

daily_summary: 2 blocks, at most 1 run(s) at once
  python data_loader   generate_orders
  python transformer   summarize_by_region
  trigger every_hour: time @hourly

Project files (6):
  __init__.py
  data_loaders/generate_orders.py
  io_config.yaml
  requirements.txt
  transformers/clean_orders.py
  transformers/summarize_by_region.py

Python packages (7):
  cloudpickle==3.1.2
  numpy==2.5.3
  pandas==3.0.6
  ...
```

Read it before you build:

- **Blocks:** every block of every pipeline, with its language. A block the service cannot
  run (a sensor, a dynamic block) stops the export and names the reason. The service does
  not check data contracts or run monitors; the notes list each one the pipeline has.
- **Project files:** only the files the blocks need, found by following their imports.
  `generate_orders` is shared by both pipelines and copied once.
- **Environment variables:** the ones the code reads, marked secret when they look like
  one. This project reads none; when it does, they are listed here and in `.env.example`.
- **Python packages:** only those the blocks import, pinned to the versions of your MageML
  environment.

The folder is a Docker build context:

| File | |
| --- | --- |
| `Dockerfile`, `compose.yaml` | Build and run the image |
| `service.json` | The pipelines, blocks, triggers, retries and timeouts |
| `shop/` | The project files the blocks need |
| `requirements.txt` | The pinned Python packages |
| `.env.example` | The variables the code reads, without values |
| `deploy/`, `.tekton/` | Kubernetes, IBM Cloud Code Engine and Tekton files |
| `report.txt`, `README.md` | The report above and how to run this service |

## 2. Build the image

```bash
docker build -t shop ./shop-service
```

The first build compiles the service (Rust) and installs the Python packages, which takes a
few minutes; later builds reuse Docker's cache. This image is 460 MB. The build ends with
`mage-service validate`, which checks the exported files, so a broken export fails here and
not in production.

## 3. Run a pipeline once

For a cron job, a Kubernetes Job or a CI step, run one pipeline and exit:

```bash
docker run --rm shop run load_orders --var rows=500
```

```text
COMPLETED load_orders  run 01a12938-bd84-7076-8c99-b0a2a292aa72  756 ms
  ok    generate_orders     751 ms
  ok    clean_orders          4 ms
```

The two blocks ran as one chain in one Python process. The first block's time includes
starting that process.

The exit code is 0 when every block completes and 1 otherwise. `--var` sets the run's
variables, as runtime variables do in MageML (`kwargs['rows']` in the block).

## 4. Serve it

```bash
export TOKEN=$(openssl rand -hex 32)   # keep it: every API call needs it
docker run -d --name shop -p 127.0.0.1:8080:8080 \
  -e MAGE_SERVICE_TOKEN="$TOKEN" \
  -v shop-data:/var/lib/mage-service \
  shop
```

Or `docker compose up --build` in the folder, which does the same with `compose.yaml`.

- `MAGE_SERVICE_TOKEN` protects the API. The service does not start without it when other
  hosts can reach it; `compose.yaml` reads it from `.env` or the shell.
- The volume keeps the run history and logs across restarts.
- Time triggers do not run until you add `-e MAGE_SERVICE_SCHEDULES=on`, so a service built
  next to a running MageML does not run the same schedule twice.

## 5. Start runs through the API

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  "http://localhost:8080/v1/pipelines/load_orders/runs?wait=60" \
  -d '{"variables": {"rows": 50000}}'
```

With `?wait=60` the call returns when the run ends (or after 60 seconds) with the status of
the run and of each block. A failing run says which block failed and why:

```json
{
  "status": "failed",
  "blocks": [
    {"block": "generate_orders", "status": "failed", "error": "1 of 1 tests failed: test_output"},
    {"block": "clean_orders", "status": "upstream_failed", "error": "Upstream block generate_orders failed."}
  ]
}
```

Other calls: `GET /v1/runs` lists runs, `GET /v1/runs/{id}/logs` returns everything the
blocks printed, `POST /v1/runs/{id}/cancel` cancels. See the
[API reference](/production/pipeline-services#3-call-it).

## One service or several

A group of pipelines in one service shares one image, one API, one run history and one
limit on runs at once (`MAGE_SERVICE_MAX_RUNS`, 8 by default); each pipeline keeps its own
concurrency setting from MageML. Put pipelines together when they share code, data and
release schedule. Export them as separate services when they need to scale apart, read
different secrets, or ship at different times.

## Streaming pipelines

A streaming pipeline exports the same way. The service runs it from its start, with no
trigger: it reads its source without end and runs the transformers on each batch.

| Part | What services run now |
| --- | --- |
| Source | Kafka, RabbitMQ, or webhooks (`connector_type: webhook`), set up in YAML |
| Transformers | Python |
| Sinks | Kafka, RabbitMQ, HTTP, Feast; `dummy` prints each message to the service's output |

```yaml
connector_type: kafka
bootstrap_server: "{{ env_var('KAFKA_BOOTSTRAP') }}"
topic: orders
consumer_group: orders-clean
batch_size: 250    # messages per batch
timeout_ms: 200    # a smaller batch runs after this long
security_protocol: SASL_SSL
sasl_config:
  mechanism: PLAIN
  username: "{{ env_var('KAFKA_USER') }}"
  password: "{{ env_var('KAFKA_PASSWORD') }}"
```

- The settings go into the service's manifest with `env_var()` kept as a reference. The
  service reads those variables itself; the blocks never get them.
- A position moves on only after every sink took the batch. A batch that still fails
  after its retries (the pipeline's retry settings, 3 by default) stops the stream, and
  the position stays where it was, so no message is lost.
- A sink with `dead_letter: true` takes the messages a block fails on, each with its error
  in a `mage-error` header (and the stream's name in `mage-stream`), while the rest of their
  batch flows on; a batch is acknowledged only once both are written, and a failing
  dead-letter sink is retried until it works. When every message of a batch fails, or a
  block does not load, it is a code problem: the batch fails as a whole and stops the
  stream, nothing goes to dead letters. A block can see a message more than once while its
  batch is split to find the failing ones. In the editor, `Execute pipeline` does not write
  to the dead-letter sink.

  ```yaml
  connector_type: kafka
  bootstrap_server: "{{ env_var('KAFKA_BOOTSTRAP') }}"
  topic: orders_dead_letters
  dead_letter: true
  ```
- The export stops, with the reason, on what services can't run the same way as MageML
  yet: Python sources and sinks, other connectors, `include_metadata`, Avro, Protobuf and
  raw messages, a start `offset`, and passwords written in the file.
- The image builds the engine with the connectors the pipeline uses. Kafka support
  (librdkafka) makes the first build a few minutes longer.

### Webhooks

A `webhook` source takes JSON messages over HTTP at `POST /v1/streams/<pipeline>/messages`:
a JSON array, one JSON message, or JSON lines (`Content-Type: application/x-ndjson`).

```yaml
connector_type: webhook
answer_within_seconds: 30        # how long a sender waits for delivery
dedupe_window_seconds: 86400     # how long an Idempotency-Key is remembered
signature:                       # optional: an HMAC-SHA256 of the body, as GitHub sends
  header: X-Hub-Signature-256
  prefix: "sha256="
  secret: "{{ env_var('WEBHOOK_SECRET') }}"
```

```bash
curl -X POST "$SERVICE/v1/streams/orders_stream/messages" \
  -H "Authorization: Bearer $MAGE_SERVICE_INGEST_TOKEN" \
  -H "Idempotency-Key: order-1042" \
  -d '[{"order_id": 1042, "amount": 12.5}]'
```

- The answer is `200` only once every sink took the messages. `503` with `Retry-After` means
  the stream is busy or stopped, `504` that delivery was not confirmed in time: retry with
  the same `Idempotency-Key`, and nothing is written twice within the dedupe window.
- `MAGE_SERVICE_INGEST_TOKEN` can only send messages, so senders never hold the service token.
- A request larger than the stream's batch size in bytes gets `413`.

### RabbitMQ

The `rabbitmq` source and sink take MageML's settings:

```yaml
connector_type: rabbitmq
connection_host: rabbitmq.example.com
connection_port: 5672
url_protocol: amqps              # amqp or amqps
amqp_url_virtual_host: orders
username: orders
password: "{{ env_var('RABBITMQ_PASSWORD') }}"
queue_name: orders
batch_size: 250                  # source: messages per batch
batch_timeout: 0.2               # source: seconds before a smaller batch runs
prefetch_count: 1000             # source: deliveries the broker sends ahead
```

- Blocks get each message as MageML's RabbitMQ source hands it, `Payload(method,
  properties, body)` with `body` in bytes, so blocks written for MageML run unchanged.
  The service acknowledges deliveries itself after the sinks: blocks must not ack them, and
  `consume_config.auto_ack` is refused.
- A delivery is acknowledged only once every sink took its batch. Deliveries not acknowledged
  when the service stops or dies go back to the queue, so a restart repeats at most the
  batches that were in flight.
- The sink publishes persistent, mandatory messages and waits for the broker's publisher
  confirms. A message no queue takes, or one the broker refuses, stops the stream with the
  reason, and its input stays unacknowledged. A sink takes `exchange` and `routing_key`
  (the queue by default); each message's `message_id` is `<stream>:<partition>:<position>`,
  the same on a replay, for consumers that dedupe.
- One queue has no partitions: several service instances share it as competing consumers,
  so order holds only with one instance.

### HTTP and Feast sinks

An `http` sink posts each batch to a URL, as a JSON array (or JSON lines with
`format: ndjson`), with `Idempotency-Key: <stream>:<partition>:<first>-<last>`, the same on
every retry of the batch. A `feast` sink pushes each batch's rows, JSON objects, to a Feast
feature server's push source.

```yaml
connector_type: http
url: https://hooks.example.com/orders
format: json
timeout_seconds: 10
headers:
  Authorization: "Bearer {{ env_var('HOOK_TOKEN') }}"
```

```yaml
connector_type: feast
url: "{{ env_var('FEAST_URL') }}"
push_source_name: driver_stats_push
to: online                 # online, offline or online_and_offline
```

- A batch counts as written only on a `2xx` answer. Network errors and `408`, `429`, `5xx`
  answers are retried; other answers stop the stream with the receiver's reason, keeping its
  position. Feast answers `500` for a row it cannot write, so a Feast sink tries a `500` three
  times and then stops the stream with Feast's reason.
- Requests never follow redirects, verify TLS, and never go to loopback, private, link-local
  or cloud metadata addresses, checked on the addresses the client connects to. A sink inside
  your own network sets `allow_private: true`.
- Feast online pushes are upserts by entity and event time, so a batch replayed after a crash
  writes the same values again; offline pushes append, so a replay can add rows twice there.
- Values are sent exactly as the blocks made them: large integers keep every digit.
- Headers whose names look like credentials (`Authorization`, tokens, keys) must be
  `env_var()` references.

## Update the service

After you change the pipelines in MageML, export again over the same folder and rebuild:

```bash
mage export service shop load_orders daily_summary --out ./shop-service --name shop
docker build -t shop ./shop-service
```

The new export replaces the exported files and keeps yours: `.env` and other `.env.*`
files (except `.env.example`, which is regenerated) and a `data/` folder. `--force` is
needed only to export into a folder that holds something other than an earlier export.
