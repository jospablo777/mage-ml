<Note>
Running a block from the code editor, while developing a pipeline, won’t use this executor.
Instead, the block is executed in the same process that the code editor is running on.
</Note>

If your MageML app is deployed in a **Kubernetes cluster**, you can configure the **Kubernetes Executor** (`executor_type: k8s`) to run each block in its own Kubernetes pod.

**Defaults:**
- Namespace: `default`
- **Job name format:** `mage-data-prep-block-{block_run_id}` (the leading `mage` is `MAGE_CLUSTER_UUID`)
- The job's container uses the image, volumes, tolerations and node selector of the MageML server pod unless the config overrides them.

You can override these defaults at the **project level**, **pipeline level**, **block level**, or with a **full Kubernetes job template**.

A block with the Kubernetes executor runs alone in production runs: it is not fused with
other blocks. See [Block fusion](/design/data-pipeline-management#block-fusion).

## Basic Setup

To configure a pipeline block to use Kubernetes executor, you simply just need to update the `executor_type` of the block to `k8s` in pipeline's metadata.yaml:

```yaml
blocks:
- uuid: example_data_loader
  type: data_loader
  upstream_blocks: []
  downstream_blocks: []
  executor_type: k8s
  ...
```
By default, MageML uses `default` as the Kubernetes namespace. You can customize the namespace by setting the `KUBE_NAMESPACE` environment variable.

```bash
export KUBE_NAMESPACE=my-namespace
```

## Configuration Methods

You can configure Kubernetes Executor in several places:

1. A full Kubernetes job template in the file at `K8S_CONFIG_FILE`
2. Project-level `k8s_executor_config`
3. Pipeline-level `executor_config`
4. Block-level `executor_config`

For a block run, MageML takes the project-level `k8s_executor_config` and applies the
block's `executor_config` on top. For `run_pipeline_in_one_process: true`, MageML uses
the pipeline-level Kubernetes executor and applies the pipeline's `executor_config` on
top of the project-level config, because the whole pipeline runs in one pod.

The merge replaces top-level keys: a block that sets `resource_limits` replaces the whole
project-level `resource_limits`, and a block that sets `pod` replaces the whole
project-level `pod`. Keys from the `K8S_CONFIG_FILE` template apply only when the inline
config does not set the same top-level key. Resource requests and limits are applied to
the job container after the pod template is built, so `resource_requests` and
`resource_limits` take precedence over `container.resources`.

### 1. Project-Level Configuration

Set `k8s_executor_config` in the project's `metadata.yaml` to apply defaults to
all blocks and pipeline runs that use the Kubernetes Executor in that project:

```yaml
k8s_executor_config:
  job_name_prefix: data-prep
  namespace: default
  resource_limits:
    cpu: 1000m
    memory: 2048Mi
  resource_requests:
    cpu: 500m
    memory: 1024Mi
  service_account_name: default
  pod:
    node_selector:
      workload: batch
    tolerations:
      - key: "workload"
        operator: "Equal"
        value: "batch"
        effect: "NoSchedule"
```

**Use when:**
You want consistent Kubernetes settings across a project, such as default
CPU/RAM, namespace, service account, or node scheduling.

### 2. Pipeline-Level Configuration

Add `executor_type: k8s` and `executor_config` to the pipeline's
`metadata.yaml`. Pipeline-level config applies to the pipeline executor when
`run_pipeline_in_one_process: true`. It does not apply to block runs.

```yaml
executor_type: k8s
run_pipeline_in_one_process: true
executor_config:
  namespace: default
  resource_limits:
    cpu: 2000m
    memory: 4096Mi
  resource_requests:
    cpu: 1000m
    memory: 2048Mi
```

**Use when:**
You run the entire pipeline in one Kubernetes pod with
`run_pipeline_in_one_process: true`.

### 3. Block-Level Configuration

Add `executor_type: k8s` and `executor_config` to a block in the pipeline's
`metadata.yaml`:

```yaml
blocks:
- uuid: example_data_loader
  type: data_loader
  executor_type: k8s
  executor_config:
    namespace: default
    resource_limits:
      cpu: 1000m
      memory: 2048Mi
    resource_requests:
      cpu: 500m
      memory: 1024Mi
```

**Use when:**
You only want to:
* Run certain blocks in the Kubernetes executor
* Override the Kubernetes executor config for specific blocks

* The Kubernetes job name is in this format: `mage-{job_name_prefix}-block-{block_run_id}`.
  The default `job_name_prefix` is `data-prep`.
  You can customize it in the `k8s_executor_config`.
  You can interpolate the trigger name in the `job_name_prefix` field with the format `{trigger_name}`.

- **GPU Support:**
  ```yaml
  k8s_executor_config:
    resource_limits:
      nvidia.com/gpu: 1  # request 1 GPU
    pod:
      node_selector:
        accelerator: nvidia-tesla-v100
      tolerations:
        - key: "nvidia.com/gpu"
          operator: "Exists"
          effect: "NoSchedule"
  ```
  Make sure [GPU device plugins](https://kubernetes.io/docs/tasks/manage-gpus/scheduling-gpus/#using-device-plugins) are installed.

- **Custom container & job spec:**
  ```yaml
  k8s_executor_config:
    container_config:
      image: <your-registry>/mageml:latest
      env:
      - name: USER_CODE_PATH
        value: /home/src/k8s_project
    job:
      active_deadline_seconds: 120
      backoff_limit: 3
      ttl_seconds_after_finished: 86400
  ```

**Use when:**
You need specialized resources or scheduling for one expensive block without
changing the rest of the pipeline.


### 4. Full Kubernetes Job Template (maximum control)

Set the `K8S_CONFIG_FILE` environment variable to the path of a YAML
configuration file. This is the raw job template for Kubernetes executor jobs.

**Example template:**

```yaml
metadata:
  annotations:
    application: "mage"
    component: "executor"
  labels:
    application: "mage"
    type: "spark"
  namespace: "default"

pod:
  service_account_name: "mage-service-account"
  image_pull_secrets: "my-registry-secret"
  node_selector:
    node-type: "compute"
    instance-type: "c5.xlarge"
    zone: "us-west-1a"
  scheduler_name: "custom-scheduler"
  tolerations:
    - key: "nvidia.com/gpu"
      operator: "Exists"
      effect: "NoSchedule"
    - key: "spot-instance"
      operator: "Equal"
      value: "true"
      effect: "NoSchedule"
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: "node-type"
                operator: "In"
                values: ["compute", "gpu"]
              - key: "instance-type"
                operator: "In"
                values: ["c5.xlarge", "c5.2xlarge"]
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          preference:
            matchExpressions:
              - key: "zone"
                operator: "In"
                values: ["us-west-1a", "us-west-1b"]
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels:
              app: "mage-pipeline"
          topologyKey: "kubernetes.io/hostname"
  volumes:
  - name: data-pvc
    persistent_volume_claim:
      claim_name: mage-data-pvc
  - name: config-volume
    config_map:
      name: mage-config
  - name: secret-volume
    secret:
      secret_name: mage-secrets
  - name: empty-dir-volume
    empty_dir: {}

container:
  name: "mage-data"
  image: "<your-registry>/mageml:latest"
  image_pull_policy: "IfNotPresent"
  env:
    - name: "KUBE_NAMESPACE"
      value: "default"
    - name: "secret_key"
      value: "somesecret"
  resources:
    limits:
      cpu: "1"
      memory: "1Gi"
      nvidia.com/gpu: 1
    requests:
      cpu: "0.1"
      memory: "0.5Gi"
      nvidia.com/gpu: 1
  volume_mounts:
    - mount_path: "/tmp/data"
      name: "data-pvc"
    - mount_path: "/etc/config"
      name: "config-volume"
    - mount_path: "/etc/secrets"
      name: "secret-volume"
      read_only: true
```

## Node Scheduling Configuration

### Node Selector
Use `node_selector` to schedule pods on specific nodes based on labels:

```yaml
k8s_executor_config:
  pod:
    node_selector:
      node-type: "gpu"           # Schedule on GPU nodes
      instance-type: "c5.large"  # Schedule on specific instance types
      zone: "us-west-1a"         # Schedule in specific availability zones
```

### Tolerations
Use `tolerations` to allow pods to be scheduled on tainted nodes:

```yaml
k8s_executor_config:
  pod:
    tolerations:
      - key: "nvidia.com/gpu"
        operator: "Exists"
        effect: "NoSchedule"
      - key: "spot-instance"
        operator: "Equal"
        value: "true"
        effect: "NoSchedule"
```

### Affinity Rules
Use `affinity` for advanced scheduling rules:

```yaml
k8s_executor_config:
  pod:
    affinity:
      # Node affinity - prefer specific node types
      nodeAffinity:
        requiredDuringSchedulingIgnoredDuringExecution:
          nodeSelectorTerms:
            - matchExpressions:
                - key: "node-type"
                  operator: "In"
                  values: ["compute", "gpu"]
        preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            preference:
              matchExpressions:
                - key: "zone"
                  operator: "In"
                  values: ["us-west-1a", "us-west-1b"]

      # Pod anti-affinity - avoid co-locating similar pods
      podAntiAffinity:
        requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: "mage-pipeline"
            topologyKey: "kubernetes.io/hostname"
```

### Custom Scheduler
Use a custom scheduler for advanced scheduling logic:

```yaml
k8s_executor_config:
  pod:
    scheduler_name: "custom-scheduler"
```

**Use when:**
You need full control over pod specs, annotations, volume mounts, and other Kubernetes settings.


## Multi-Container Pods

If your MageML deployment runs in a **multi-container pod**, set the `MAGE_CONTAINER_NAME` environment variable to specify which container runs MageML:

```yaml
env:
  - name: MAGE_CONTAINER_NAME
    valueFrom:
      fieldRef:
        fieldPath: metadata.name
```

If not set, MageML defaults to the **first container** in the pod.


## Environment Variables Reference

### General Configuration

| Variable               | Purpose                                         | Default |
|------------------------|-------------------------------------------------|---------|
| `KUBE_NAMESPACE`       | Namespace for job execution                     | default |
| `K8S_CONFIG_FILE`      | Path to full Kubernetes job config file         |         |
| `MAGE_CONTAINER_NAME`  | Container that runs MageML in multi-container pods |      |

**Priority order** (highest to lowest):
1. Block-level `executor_config` in the pipeline's `metadata.yaml` (block runs), or
   pipeline-level `executor_config` (pipelines run in one pod)
2. Project-level `k8s_executor_config` in the project's `metadata.yaml`
3. The job template in `K8S_CONFIG_FILE`
4. Hardcoded defaults
