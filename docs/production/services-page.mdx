MageML exports pipelines as a [pipeline service](/production/pipeline-services): one Docker
image that runs them without MageML. The app does it in two places:

| Where | Use it to |
| --- | --- |
| **Export as service** in the pipelines list (right-click a pipeline) and in the editor's **File** menu | Export one or more pipelines now |
| **Services** in the left menu | Save a service in the project, check its configuration, chain its pipelines, export, build and push it |

Both run the same export as `mage export service`. The [tutorial](/getting-started/service-tutorial)
goes through them with the playground.

- Choose the pipelines on the left. Each row shows its blocks, languages and triggers.
- The preview on the right updates as you choose: what the image will hold, the environment
  variables the container needs, and anything that stops the export, such as a sensor
  block, with its reason.
- **Export** writes the build context with a progress bar, then shows the next steps:
  download it as a zip, build and ship the image, run it and deploy it.

The service name names the image and the folder. **Runs of one pipeline at the same
time**, under **Advanced options**, overrides each pipeline's limit: a run that starts while
that many are running waits in the queue and starts when one finishes. Keep 1 for
pipelines that must not overlap, such as an incremental load that moves a cursor.

## The Services page

**Services** keeps each service in the project, in its own folder, so services go to Git with
the pipelines they run and a pull request shows what changed:

```
services/
  shop-live/
    service.yaml            # the service: pipelines and settings
    environments/dev.yaml   # where and how it runs
    service.lock            # written by mage service build; commit it
```

`service.yaml`:

```yaml
name: shop-live
pipelines: [live_traffic, live_minute_kpis, live_device_revenue]
description: Live shop traffic, then per-minute KPIs after each traffic run
max_runs: 2           # optional: runs of each pipeline at once
include: [models/churn.onnx]   # optional: files the blocks reach by a computed path
model_registry: http://mlflow.ml.svc:5000   # optional: where models come from
models:                                     # optional: models embedded in the image
  - name: churn
    uri: models:/churn-classifier@champion
```

The same services from the command line, in the project folder:

| Command | What it does |
| --- | --- |
| `mage service new shop-live --pipelines live_traffic,live_minute_kpis` | Creates the folder with `service.yaml` and a `dev` environment |
| `mage service list` | The services, their pipelines and where each is saved |
| `mage service check shop-live` | What would stop the service from building, and what to know |
| `mage service check --affected [--base origin/main]` | Checks the services that the changes since `--base` touch, for CI ([below](#check-the-services-a-change-touches)) |
| `mage service test shop-live` | Runs each stream sample through the blocks a sink follows ([below](#test-before-deploying)) |
| `mage service run shop-live [--env dev] [--port 6790]` | Runs the service on this machine's engine, without Docker, until Ctrl+C ([below](#run-a-service-locally)) |
| `mage service build shop-live [--image]` | Writes the build to `.mage/build/shop-live/` (kept out of Git) and updates `service.lock` |
| `mage service deploy shop-live --env prod` | Builds the image, runs it in the environment's target, waits for health and brings the previous deployment back on failure ([below](#deploy-with-docker)) |
| `mage service status [shop-live]` | Per environment: what runs and whether it is the repository version |
| `mage service diff shop-live --env prod` | The service's files changed since the deployed commit |
| `mage service rollback shop-live --env prod` | Runs the previous deployment again |
| `mage service export shop-live --out ./shop-live` | The build context in a folder, for a team that builds elsewhere |
| `mage service migrate` | Moves the services of the earlier `pipeline_services.yaml` to their folders |

`service.lock` pins what a build used: the manifest, the project files, the requirements, the
models' versions and the engine. It has no timestamps, so it changes only when one of them
changed, and its diff in a pull request says what moved.

Projects that still have `pipeline_services.yaml` keep working: its services are read, and
saving one on the Services page moves it to its folder.

`mage service run shop-live --reload` starts the service again, from a new build, when a
file it reads changes (its blocks, shared code, `io_config.yaml`, the service folder and
`.env.<env>`). A build that fails is shown and waits for the next change.

### Deploy with Docker

An environment with `target: docker` deploys to the Docker of this machine:

```yaml
# services/shop-live/environments/prod.yaml
target: docker
port: 6800           # the host port, on 127.0.0.1
schedules: on        # the service runs its time triggers
variables:
  REGION: eu
```

`mage service deploy shop-live --env prod` checks the service, builds it (updating
`service.lock`), builds the image `mage-shop-live:<lock digest>` and starts the container
`mage-shop-live-prod`, with the environment's variables, the secrets of
`services/shop-live/.env.prod` (passed in a private file, never on the command line) and an
API token in `.mage/deploy/shop-live/prod/token`. Run history and stream positions are kept
in the volume `mage-shop-live-prod-data`.

- What runs must be a commit. When the service's inputs (its folder, its pipelines and
  blocks, shared code, `io_config.yaml`, `requirements.txt`) have uncommitted changes, or the
  build updated `service.lock`, the deploy lists them and stops. Commit them, or deploy anyway
  with `--allow-uncommitted "<reason>"`: the reason goes on the container and `status` shows
  it.
- The container carries labels with the commit, the lock and the image, so `status` and
  `diff` read what runs from Docker; nothing is committed back.
- The deploy waits for `/healthz`. When the new container does not become healthy, it is
  removed, its last log lines are shown, and the previous deployment runs again.
- The previous deployment is kept, stopped, as `mage-shop-live-prod-previous`:
  `mage service rollback shop-live --env prod` swaps them.

The Services page lists each service's deployments under its name: the environment and
whether it runs the repository's version, is behind it, or is stopped.

### Deploy to Kubernetes

An environment with `target: kubernetes` deploys with kubectl. The context is required, so
a deploy never goes to whichever cluster happens to be current:

```yaml
# services/shop-live/environments/prod.yaml
target: kubernetes
context: prod-cluster          # the kubectl context
namespace: shop                # default: default; it must exist
image: icr.io/team/shop-live   # pushed as icr.io/team/shop-live:<lock digest>
platforms: [linux/amd64]       # optional: the cluster's platform
image_pull_secret: icr         # optional
storage: 5Gi                   # optional: the run history volume
storage_class: ibmc-block-gold # optional
resources:                     # optional, as in a pod spec
  limits: {memory: 1Gi}
schedules: on
variables:
  REGION: eu
```

`mage service deploy shop-live --env prod` builds and pushes the image, then applies the
Deployment, Service and volume claim `mage-shop-live-prod` and a Secret with the variables,
the secrets of `.env.prod` and the API token (sent on stdin, never on the command line). It
waits for the rollout; when the new pod does not become ready, its last log lines are shown
and `kubectl rollout undo` brings the previous revision back.

- The Secret is named by its content (`mage-shop-live-prod-env-<digest>`), so an undo also
  brings back the previous variables. Secrets older than the kept revisions are deleted.
- The commit, the lock and the image are annotations of the pod template, so `status` reads
  what runs after an undo too. `rollback` runs `kubectl rollout undo`.
- One replica, replaced with the Recreate strategy: the run history is a SQLite file on a
  ReadWriteOnce volume. `MAGE_SERVICE_INSTANCE_ID` is the pod name, for Kafka's static
  membership.
- Without `image`, the image stays in this Docker: Rancher Desktop and Docker Desktop
  clusters use it as it is, and `kind_cluster: <name>` loads it into kind.
- `runs` and `logs` reach the service through a `kubectl port-forward` that they stop
  afterwards; `logs --engine` runs `kubectl logs`.

### Deploy to IBM Cloud Code Engine

An environment with `target: code_engine` deploys through the Code Engine API with an IAM
token from `IBM_CLOUD_API_KEY` (or a trusted profile):

```yaml
# services/shop-live/environments/prod.yaml
target: code_engine
region: eu-de
project_id: 0f9c1e3a-...          # the Code Engine project's ID
image: icr.io/team/shop-live      # pushed as icr.io/team/shop-live:<lock digest>, for amd64
image_secret: icr-secret          # optional: the project's registry access secret
cpu: "1"                          # optional
memory: 2G                        # optional
visibility: public                # public (default), private or project
variables:
  REGION: eu
```

`mage service deploy shop-live --env prod` pushes the image, creates the Secret
`mage-shop-live-prod-env-<digest>` with the variables, the secrets of `.env.prod` and the API
token, and creates or updates the app `mage-shop-live-prod` with one instance, always on. It
waits for a new revision to be ready; when it is not, the app is patched back as it was.

- Code Engine keeps only one inactive revision, so the app records the previous image and
  Secret itself: `rollback` swaps them, and a second `rollback` swaps them back.
- `status`, `runs` and `logs` use the app's URL; `logs --engine` runs
  `ibmcloud ce app logs` with the API key, in a CLI home of its own.
- Code Engine apps have no persistent volume: run history, and the positions of sources the
  engine keeps itself, start empty when the instance is replaced. Kafka keeps its offsets in
  Kafka, so Kafka streams resume.

`deploy/ibm/code-engine.sh` in the build context remains for building from source in Code
Engine.

### Call a service

`mage service call shop-live` runs the service's pipeline (name it when there are several)
and prints each block's status and the output of the last block that has one:

```bash
mage service call shop-live --var day=2026-10-17 --var limit=500   # the local run
mage service call shop-live orders --env prod --block score        # a deployment
```

`--var` values are JSON when they parse as JSON, text otherwise. A failed run exits with 1
and names the command that prints its log.

### Runs and logs

`mage service runs` and `mage service logs` read a running service's API, with its token.
Without `--env` they talk to the service that `mage service run` started; with `--env`, to
that environment's deployment.

```bash
mage service runs shop-live --env prod --status failed   # the latest failed runs
mage service logs shop-live --env prod                   # the latest run's log
mage service logs shop-live --env prod --run <id> --block load --tail 50
mage service logs shop-live --env prod --engine -f       # the engine's own log, followed
```

`runs` shows each run's pipeline, status, source (`api`, `schedule:<trigger>`), start,
duration and the first line of its error. `--engine` prints the container's log: start-up,
schedules and stream errors, which belong to no run.

### Check the services a change touches

In CI, `mage service check --affected --base origin/main` lists the services that the
changes since `origin/main` (committed or not) touch, and checks each: a change to a
service's folder, its pipelines, the code its blocks import, its stream settings,
`io_config.yaml`, `requirements.txt` or the project's `metadata.yaml` counts. It exits with 1
when a check fails, and does nothing when no service is affected.

`--locked` also fails when a build would change the committed `service.lock`, so a pull
request cannot merge a lock that a deploy would refuse.

### CI and CD workflow

`mage service ci` writes `.github/workflows/mage-services.yml` at the repository's root:

```bash
mage service ci --deploy dev=main --deploy 'prod=tag:v*'
```

- Pull requests run `mage service check --affected --locked --tests` against their base
  branch.
- Each `--deploy ENV=BRANCH` or `ENV=tag:PREFIX*` rule deploys the services that define the
  environment, one job per service, with the GitHub environment `ENV` (for its secrets and
  required reviewers). `mage service deploy --if-changed` builds nothing when the
  environment already runs the lock with the same values.
- A service's secrets come from the environment secret `<SERVICE>_<ENV>_ENV` (for example
  `SHOP_LIVE_PROD_ENV`), its `.env.<env>` as `KEY=value` lines. `KUBECONFIG` holds the
  contexts the environments name, and `REGISTRY_USERNAME` and `REGISTRY_PASSWORD` push the
  images.
- The rules deploy Kubernetes environments; an environment that deploys to Docker is
  refused, since in CI that is the runner's Docker.
- A deploy keeps the API token of the running deployment, so clients keep working; set
  `MAGE_SERVICE_TOKEN` in the environment secret to choose it.

- `--promote prod=staging` makes the `prod` rule deploy the image `staging` runs instead of
  a new build (see below).

The workflow is yours to edit; `mage service ci --force` writes it again.

### Promote from one environment to the next

`mage service deploy shop-live --env prod --from staging` deploys the image that staging runs,
with its lock and commit, so production runs exactly what staging tested. Nothing is built;
prod keeps its own variables, secrets and API token, and `status` shows `promoted from
staging`. When prod pulls from another repository, the image is tagged and pushed there
first (so this machine or the CI job needs access to both registries). Staging must be
running.

### Outputs that consumers read

When a block of the service has a [data contract](/guides/blocks/data-contracts), `service.lock`
records the columns it declares. A rebuild that would break the readers of that output stops,
with the changes listed: a column removed, a column whose type changed, or a column that may
now be missing. Adding a column breaks nothing. To make the change anyway, give the reason:

```bash
mage service build shop-live --allow-breaking "order ids become strings"
```

The reason and the changes go into `service.lock`, so the pull request that makes the change
shows them; `deploy` takes the same option.

### Test before deploying

A stream's [samples](/guides/streaming/introduction) are the service's tests. `mage service
test shop-live` runs each sample of each stream pipeline through the blocks whose output a
sink writes (and any transformer nothing follows), as Run on sample does, and lists each
result with its time:

```text
live_traffic · example (5 messages) → live_traffic_parse: passed in 12 ms
1 of 1 tests passed.
```

`deploy` runs them before it builds and stops when one fails. To deploy anyway, give the
reason; it is recorded on the deployment:

```bash
mage service deploy shop-live --env prod --skip-tests "the sample predates the new schema"
```

A stream without samples has no tests; batch pipelines have none yet. Samples are kept out
of Git by default, since captured messages can hold real data, so CI runs only the samples
committed: write the ones that should guard a deploy, and commit them.

### Run a service locally

`mage service run shop-live` builds the service into `.mage/run/shop-live/` and runs it on
the engine, `mage-service`, with the Python running MageML: the same API, schedules and
streams as the image, without Docker.

- **The engine.** `uv pip install "mage-ml[services]"` installs it next to Python (Linux x86_64
  and aarch64 with glibc 2.28 or later, macOS on Apple silicon). Elsewhere, build it with
  `cargo build --release -p mage-service --features full` and set `MAGE_ENGINE_PATH`.
- **Values.** `environments/dev.yaml` holds the non-secret `variables`; secrets go in
  `services/shop-live/.env.dev` (`KEY=value` lines, ignored by Git). The run lists the
  variables the blocks need that are not set. `--env staging` reads `staging.yaml` and
  `.env.staging`.
- **The API token.** Each service gets one, written to `.mage/run/shop-live/token` and
  readable by you only; send it as `Authorization: Bearer <token>`.
- **State.** Run history and stream positions stay in `.mage/run/shop-live/data` across
  restarts. A local run does not change `service.lock`.
- **Rust blocks** are compiled with cargo, as the image does.

```bash
mage service run shop-live
curl -X POST "http://127.0.0.1:6790/v1/pipelines/live_minute_kpis/runs?wait=60" \
  -H "Authorization: Bearer $(cat .mage/run/shop-live/token)" -d '{}'
```

Each pipeline keeps its triggers. **Start after another pipeline** adds an
[after-run trigger](/orchestration/triggers/triggering-pipelines#after-run-triggers) to the
pipeline: it starts when a run of the other one completes, fails or ends either way. The
trigger belongs to the pipeline, so it shows on its Triggers page and MageML runs it too;
the service runs it for the pipelines it holds. The run flow below the pipelines draws the
chains. Features then scoring, or a load then its checks, become one flow with one
schedule.

### Configuration check, secrets and variables

<Frame>
  <img className="block dark:hidden" src="/images/screenshots/services-check.light.png" alt="The configuration check: 3 pipelines, 8 blocks, 1 schedule, 2 after-run triggers, every block supported, 10 project files, 18 Python packages; and the secrets and environment variables: what the pipelines read and what the service reads" />
  <img className="hidden dark:block" src="/images/screenshots/services-check.dark.png" alt="The configuration check: 3 pipelines, 8 blocks, 1 schedule, 2 after-run triggers, every block supported, 10 project files, 18 Python packages; and the secrets and environment variables: what the pipelines read and what the service reads" />
</Frame>

The check runs the export's own checks without writing anything, each time the service
changes:

- every block is supported, or why one is not;
- the project files that go in the image, and the Python packages, pinned to the versions
  MageML runs with;
- the schedules and after-run triggers, and loops between them;
- notes, such as files included because a block names them.

**Secrets and environment variables** lists what the pipelines read and what the service
reads. Every variable of `io_config.yaml` is a secret, and those of the profiles the
blocks use are required; the rest of what the pipelines read is marked secret when its
name looks secret. Then come the service's own settings, such as `MAGE_SERVICE_TOKEN`, and
where secrets can come from: the environment, files, a folder of files, or a secrets
manager (IBM Cloud, AWS). **Copy .env** gives a `.env` template with all of them. Values
never leave the app or go into the export.

### Models in the image

Add the models the blocks score with: each row is a registered model with an alias, such as
`champion`, or a version, or any URI MLflow can download, and the name blocks load it by.
**Add a model** adds another row. The MLflow tracking server is the registry; empty, the
server's `MLFLOW_TRACKING_URI` is used.

While you edit, the check resolves each row in the registry:

| Row says | Meaning |
| --- | --- |
| champion is churn-classifier version 10 (champion), run 3f2a91c0 | The alias resolves; the version's tags follow, such as `validated=true` |
| Trained on the Feast feature service churn_features_v1 | The version or its run has the `feast.feature_service` tag |
| Not found in the registry | The registry answered with the reason; the export stays off |

After **Export**, each model reports: "The model churn was embedded", with its version and
size, or "Error: the model churn could not be downloaded and embedded" with the reason.
Models the code loads with `load_model(name, uri=...)` and literal arguments are found and
embedded without a row. See [Models](/production/pipeline-services#models) for loading a
model in its own format and reading its Feast feature service.

After an export, **Build and ship the image** writes the commands for the platforms and the
registry you choose:

| Registry | Image | Login |
| --- | --- | --- |
| Docker Hub | `docker.io/<user>/<name>:<tag>` | `docker login -u <user>` |
| IBM Cloud Container Registry | `icr.io/<namespace>/<name>:<tag>` (or a regional host such as `us.icr.io`) | `ibmcloud cr login`, or an API key with user `iamapikey` |
| GitHub Container Registry | `ghcr.io/<owner>/<name>:<tag>` | a token with `docker login ghcr.io` |
| Amazon ECR | `<account>.dkr.ecr.<region>.amazonaws.com/<name>:<tag>` | `aws ecr get-login-password` |
| Google Artifact Registry | `<region>-docker.pkg.dev/<project>/<repository>/<name>:<tag>` | `gcloud auth configure-docker` |
| Azure Container Registry | `<registry>.azurecr.io/<name>:<tag>` | `az acr login` |

- **This machine** builds for the machine's own chip with `docker build`. `linux/amd64` and
  `linux/arm64` build with `docker buildx`; both together make one image that runs on
  either (most cloud servers are amd64; Apple silicon and AWS Graviton are arm64). Two
  platforms need a registry, since Docker keeps one platform of an image locally.
- **Build on the server** (or **Build and push from the server**) appears when the machine
  that runs MageML has Docker. It builds the export there and shows every line Docker prints;
  pushing uses the registries that machine is logged in to. MageML in a container usually
  has no Docker: run the commands where Docker is.

The CLI does the same: `mage service build shop-live --image --platform
linux/amd64,linux/arm64 --push --tag icr.io/ml-team/shop-live:1.0`.

## The export as a repository

The export is a folder with everything the image needs, so it builds on any machine and in
any CI:

| In the folder | What it is |
| --- | --- |
| `Dockerfile`, `compose.yaml`, `.dockerignore` | The image and a one-machine setup |
| `<project>/`, `pyproject.toml`, `uv.lock`, `rust/`, `r/` | The pipelines' code and what it needs, locked |
| `manifest.json` | Versions, lock and model digests, and the SHA-256 of every file, to review what changed between two exports |
| `service.json`, `README.md`, `.env.example`, `report.txt` | The manifest, how to run it, the variables to set, what the export found |
| `.github/workflows/build-image.yml` | GitHub Actions: builds amd64 and arm64 on every push to `main`, and pushes when the repository sets `REGISTRY_IMAGE` and the `REGISTRY_USERNAME` and `REGISTRY_PASSWORD` secrets (ghcr.io needs no secrets: the job logs in with `GITHUB_TOKEN`) |
| `.tekton/`, `deploy/ibm/` | IBM Cloud Continuous Delivery and Code Engine |
| `deploy/kubernetes.yaml` | A Deployment with probes and a volume claim |
| `.gitignore` | Leaves out `.env`, local data and build output |

Keep it as its own repository: export again into the same folder and commit the diff. The
export keeps `.git`, `.env` and `data/`.
