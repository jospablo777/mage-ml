A streaming pipeline runs on MageML's stream engine by default, one small service per
pipeline. Teams that run Spark can run the same pipeline on Spark Structured Streaming
instead, over [Spark Connect](https://spark.apache.org/docs/latest/spark-connect-overview.html).
The pipeline does not change: its Python blocks run through the engine's own worker code,
inside Spark's `mapInArrow`, so a block gives the same messages on both.

```bash
uv run --with "pyspark[connect]>=4.3" mage spark-stream . orders_clean \
  --remote sc://spark.example.com:15002 \
  --checkpoint s3a://lake/checkpoints/orders_clean \
  --env KAFKA_BOOTSTRAP=kafka.internal:9092
```

`uv run --with` brings PySpark for this command only (the `spark-connect` extra installs it
for good). Keep it out of the Mage server's own environment: there PySpark turns on Mage's
Spark pages, which start a local Spark when opened. The smaller `pyspark-client` package
works for the command, but MLflow and Great Expectations fail next to it, as they look for a
local Spark when they find `pyspark`.

The command starts the query on the server and prints its progress every 10 seconds
(`batch 12: 500 rows in, 410/s arriving, 2,300/s processed, 450 rows out`). Ctrl-C stops
it; the next run continues from the checkpoint. A block that fails stops the query with the
block's name and reason.

## Run it without MageML

`mage export spark-stream` writes a folder that runs the stream from a container of its own:
the plan (`plan.json`, whose settings keep their `env_var` and secret references), the
runner that starts and watches the query, the engine's worker code and a Dockerfile. It
needs `pyspark-client` and `pyarrow`, nothing of MageML.

```bash
mage export spark-stream . orders_clean ./orders_clean_spark
docker build -t orders-clean-spark ./orders_clean_spark
docker run -d \
  -e MAGE_SPARK_REMOTE=sc://spark.example.com:15002 \
  -e MAGE_SPARK_CHECKPOINT=s3a://lake/checkpoints/orders_clean \
  -e KAFKA_BOOTSTRAP=kafka.internal:9092 \
  orders-clean-spark
```

It writes the query's progress every `MAGE_SPARK_PROGRESS_SECONDS` (10). SIGTERM stops the
query, and the next start continues from the checkpoint; Spark stops an older run of the
same checkpoint when a new one starts, so a restarted container never leaves two. A query
that fails ends the container with exit code 1 and the reason, for the orchestrator to
restart it. Its `README.md` lists the variables to set.

## What runs on Spark

| Pipeline | On Spark |
| --- | --- |
| Kafka source: `bootstrap_server`, `topic` or `topics`, `auto_offset_reset`, `security_protocol`, `sasl_config` (PLAIN, SCRAM) | `readStream.format("kafka")` with `kafka.bootstrap.servers`, `subscribe`, `startingOffsets`, `kafka.security.protocol`, `kafka.sasl.*` |
| `batch_size` | `maxOffsetsPerTrigger` |
| `timeout_ms` | the trigger interval |
| Python stream transformers: the message list or a DataFrame, pipeline variables | `mapInArrow`, by the engine's worker code |
| Kafka sinks: `bootstrap_server`, `topic`, `security_protocol`, `sasl_config` | one: `writeStream.format("kafka")`; several: `foreachBatch`, each sink its block's messages |
| A Kafka sink with `dead_letter: true` | the messages a block fails on, as they came, with `mage-error` and `mage-stream` headers |
| The source's position, committed after the sinks | Spark's checkpoint, written after the sink |

`mage spark-stream --check` says whether a pipeline can run, without starting it. A pipeline
with anything else is refused with the list: other sources and sinks, exactly-once
delivery, event time, keyed state, SQL, window, lookup, Rust and R stream blocks. Those run on the engine. Broadcast values are set through the stream
service's API, which Spark does not have: blocks read an empty `kwargs['broadcast']`.

## Positions

Spark keeps the stream's positions in its checkpoint, never in the consumer group. A first
run starts where `auto_offset_reset` says (`earliest` or `latest`), whatever the group
committed on the engine. The checkpoint must be durable (object storage, HDFS): a lost
checkpoint starts the stream over. Delivery is at least once, as on the engine: a batch
that fails is read again.

## The Spark server

- Spark 4 with Spark Connect, and the Kafka connector
  (`org.apache.spark:spark-sql-kafka-0-10_2.13`) in its jars or `--packages`.
- Its Python workers run your Python's minor version (Spark refuses a Python UDF
  otherwise) with `pyarrow`, and the packages your blocks import. The command checks the
  version and pyarrow when it starts the query.
- With several sinks or a dead-letter sink, a `foreachBatch` function writes them; it runs
  in a Python worker that is itself a Spark Connect client, so the workers also need
  `pyspark-client`'s libraries (`grpcio`, `grpcio-status`, `googleapis-common-protos`,
  `protobuf`, `zstandard`).
- Settings that read variables (`{{ env_var('KAFKA_BOOTSTRAP') }}`, secrets) are filled in
  from the environment of the command, and `--env` sets or overrides them: the addresses
  Spark reaches can differ from yours.
