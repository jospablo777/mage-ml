Triggered runs start in warm Python workers, chains of SQL blocks run as one query, and the
server's access checks were tightened across the API. Services gain monitors, data
contracts, keyed state with timers and Python workers, and Airflow can run MageML
pipelines.

## Runs

- **Run engine**: with `mageml-engine` installed, the scheduler's jobs run in warm Python
  workers instead of a new process per block. A three-block fused run took 0.12 seconds
  instead of 1.0; the 1 million row benchmark pipelines a third of their time.
- **Compiled SQL chains** on DuckDB, PostgreSQL and ClickHouse: consecutive SQL blocks
  become views and run as one query. A four-block DuckDB chain over 30 million rows ran in
  1 s instead of 20 s and wrote 1 MB instead of 952 MB.
- **Trigger rules**: `none_failed_min_one_success` joins after the branch that ran,
  `all_done` runs cleanup and alerts after a failure.
- **Python workers**: named uv environments per block or pipeline, so a block can use
  pandas 2 next to MageML's pandas 3.
- A worker the scheduler gave up on no longer writes outputs over the newer attempt's.

## Server

- An **audit log** of every change made through the API, a **Server health** page, a
  **Dependencies** page of the pipelines that start or feed each other, and **Import and
  export** of pipelines as one zip (`mage project-export`, `mage project-import`).
- Security: the session token is an HttpOnly cookie; only owners grant admin or owner
  access; each resource of a list is checked for its own pipeline; sign-in locks after 10
  failed attempts; viewers can no longer stop the scheduler or trigger events. Next.js
  15.5.29 fixes an unauthenticated remote code execution, with updates across Python, Rust
  and JavaScript dependencies, now audited and fixed by daily workflows.

## Services

- Monitors (drift, missing values, segments, silences) and data contracts run in services.
- Keyed state and timers in Python, Rust and R stream blocks, window blocks, event time, and
  state kept in an object store.
- A PostgreSQL run history shared by several instances, models with champions and
  challengers, audit records, and alerts by email.
- SQL blocks run in services on BigQuery, Snowflake, Redshift, Db2, Trino, Druid and SQL
  Server (pymssql, no ODBC driver).

## Airflow

`MageMLServiceRunOperator` runs a service's pipeline from a DAG, `MageMLPipelineOperator`
a pipeline on a MageML server, and `mageml_asset` makes a pipeline an Airflow Asset. The
provider is in `packages/mageml-airflow`; it is not on the index yet.

## Before upgrading

Check the behavior changes in the
[release notes](https://github.com/jospablo777/mage-ml/blob/master/docs-md/development/release-notes.md),
among them: a Python transformer in an integration pipeline gets up to 10,000 records per
call (`records_per_call: 1` keeps one); `mage run` skips disabled blocks and false
conditions; a PostgreSQL run history moves to schema version 3; pages no longer read the
session token, while scripts keep sending it as a Bearer header.

`mage-integrations` 0.2.0, `column-atlas-native` 0.2.0 and `mageml-engine` 0.2.0 are new;
`singer-python` stays `5.13.0+mage.2`, unchanged, and the index keeps its published wheel.

## Install or upgrade

```bash
uv add "mage-ml==0.3.0" mageml-engine --index mageml=https://jospablo777.github.io/mage-ml/simple/
```

`mageml-engine` runs triggered runs in warm workers, and streams and services on this
machine; MageML runs without it. In a project that already has MageML:
`uv lock --upgrade-package mage-ml && uv sync`. With pip:
`python -m pip install -r https://jospablo777.github.io/mage-ml/install/v0.3.0/base.txt`.
All the ways to install are in the
[Quickstart](https://github.com/jospablo777/mage-ml/blob/master/docs-md/getting-started/setup.md).

Wheels are qualified on Linux x86-64 and ARM64 (glibc 2.28 or newer) and macOS Apple
Silicon (macOS 12 or newer), with CPython 3.12.
